# qq-bot 消息持久化队列 —— 设计

> 状态：**已实现并部署**（2026-09-21）
> 目标：解决「重启丢消息」——这是 2026-09-21 两次「机器人不回复」的真正主因

## 用户裁定

| 问题 | 决定 |
|---|---|
| 窗口期条目（`running`）如何处理 | **不重放**，改为告知用户可回「继续」手动重放 |
| 重复回复 | 可接受，优先不丢消息 |
| `queue.json` 体积上限 | **1 MB** |
| 恢复时的告知文案 | 「继续」= 重放上一条 |

## 「继续」机制（取代原设计里的自动重放告知）

启动时发现 `running` 条目 → 记入内存 `pendingRetry`（key → 原始事件）+ 回复
「刚才那条消息没处理完，回「继续」可以重新执行」。

**用户回「继续」 → 重放 `pendingRetry.get(key)` 里的事件。**

为什么是「继续」而不是自动重放：`running` 意味着 claude 可能已经跑了一部分，
重放有重复执行破坏性操作的风险（这台机器上真的会卸载软件、踢人）。
交给用户判断「我刚才那条要不要重跑」，既避免了误判，也避免了用户重打一遍。

**「继续」只在恰好有 pending 条目时拦截**；没有待重放时
（如开机自启的干净启动）它就是普通闲聊词，照常走模型。

原定的「等用户重发」已废弃 —— 用户要重打一遍太麻烦，记不住原文。

## 问题

`handleMessage` 的队列完全在内存里（[index.js:80](../../../D--QQBOT/qq-bot/src/index.js) 的 `queues`：`Map<string, Promise>`）。
进程重启时：

- **已入队的待处理消息** → 随进程消失，**静默丢弃，无任何日志**
- **正在执行的消息** → 子进程被强杀，用户永远等不到回复，同样无日志

只留下一条「收到 xxx」然后什么都没有 —— 排查时和「消息压根没收到」无法区分。

## 关键约束（已实测验证，不是推测）

### 1. pm2 通过 taskkill /F 强杀，不给收尾机会

证据链：

| 环节 | 事实 |
|---|---|
| `God.killProcess` 分支 | 未显式设 `kill_timeout` → `pm2_env.treekill === true` → 走 treekill |
| `lib/TreeKill.js` win32 分支 | `exec('taskkill /pid <pid> /T /F')` |
| `/F` 的含义 | **强制终止，不发送任何信号** |
| 实测 | 设 `--kill-timeout 10000` + 9 秒延时处理器，处理器从未触发 |

**推论：SIGINT/SIGTERM 处理器在 pm2 重启时永远不执行。**
「收到信号 → 落盘 → 退出」这套优雅关闭方案**在此环境下不成立**，不要尝试。

### 2. 因此无法区分「正在执行」与「刚被杀」

子进程树的存活探测可以告诉我们 claude 进程还在不在，但那只能证明它**被杀了**，
不能证明它**没跑完**——而 kill 恰好总会让它消失。

剩下的选择只有：窗口期条目**重放**（可能重复执行）或**丢弃**（可能漏执行）。
用户已裁定：**丢弃 + 告知**。

### 3. 孤立代理会损坏文本

`text.slice(0, 80)` 若把 emoji 的代理对切一半，落盘后该字符变成 `�`（已实测）。
不一定抛错，但会静默污染数据。持久化前必须清理。

## 设计

### 存储

单文件 `D:\QQBOT\qq-bot\queue.json`，**不用 SQLite**——这与 `sessions.json` / `roles.json`
的既有风格一致，且用 `rename` 原子替换即可满足需求（队列深度个位数，非高并发场景）。

```
queue.json.tmp  --write-->  rename  -->  queue.json     （原子，避免半截文件）
```

每条目自带 `key`（复用 `conversationKey`），**不按会话分文件**：
多条消息共用一个 conversation key 是常态（连发问题），分文件会让追加变复杂。

### 条目结构

```jsonc
{
  "id": "1789980640000-0",         // 条目唯一 id，状态追踪按它走（见下）
  "key": "894815246:1765116032",   // conversationKey，决定重放后的排队顺序
  "event": { ...原始 OneBot 事件... },  // 原样存，重放时走同一条 handleMessage 路径
  "status": "queued" | "running",
  "at": 1789980640000
}
```

**`status` 是避免重复执行的核心**，而它必须挂在**条目 id** 上而非 key 上。详见下节。

### 为什么按条目 id 而不是按会话 key 追踪

这是实现中途验证时发现并修掉的缺陷。用户连发两条时，队列里同 key 有两条，
但**同一时刻只有队首在执行**：

- 按 **key** 标记 → 两条都被标成 `running` → 第二条（**从未执行过**）
  在恢复时被误判为「状态未知」，不敢自动重放，要用户手动回「继续」
- 按 **id** 标记 → 只有队首变 `running`，第二条保持 `queued` → 自动恢复 ✅

即：按 key 会把本该自动恢复的消息降级成需要人工确认。

### 写入时机

| 时机 | 写入内容 | 目的 |
|---|---|---|
| `enqueue` 时 | 追加 `status:"queued"`，返回 `id` | 消息一到达就落盘，覆盖「已入队未开始」的丢失窗口 |
| `handleMessage` 开头 | 该 `id` 改为 `status:"running"` | 标记执行中 |
| 处理完成、**发送回复之前** | 删除该 `id` | 先摘除再发送：若摘除失败最多让用户回一次「继续」；反过来则会重复发送 |

### 启动时恢复

```
读 queue.json（体积 > 1MB 则整体丢弃并告警）
  ├─ status:"queued"   → 重新入队（这批消息**确定尚未开始执行**，重放安全）★主要价值
  └─ status:"running"  → 不自动重放，存入内存 pendingRetry 并告知用户可回「继续」
```

**为什么 `status` 能保证安全**：读到 `queued` 说明进程在把它改成 `running` 之前就死了，
该消息**确实没有被执行过**——这不是启发式猜测，是状态机的事实。

## 体积上限

`queue.json` 超过 **1 MB** 时：整体丢弃 + `log` 告警。

单个事件约 1–2 KB，1 MB 约合 500–1000 条积压 —— 正常情况（个位数条目）远达不到，
触发即说明有严重积压或异常，此时宁可丢弃也不要让恢复流程卡住。

### 实现改动点

| 文件 | 改动 |
|---|---|
| `src/queue.js` | 新增模块：`loadEntries` / `markQueued` / `markRunning` / `removePending` / `setQueuePath` / `setQueueLogger` |
| `src/index.js:enqueue` | 入队时 `markQueued` 拿到 `entryId`，透传给 `handleMessage` |
| `src/index.js:handleMessage` | 开头 `markRunning(entryId)`，成功回复后 `removePending(entryId)` |
| `src/index.js:restoreQueue` | 启动恢复；`queued` 自动重放，`running` 进 `pendingRetry` 并询问「继续」 |
| `src/index.js:handleRetry` | 拦截「继续」（仅在有 pending 时），重放对应事件 |
| `tests/queue.test.js` | 13 项：原子写、损坏告警、体积上限、按 id 追踪、连发场景 |

原子写实现：写 `.tmp` → `fs.renameSync`（Windows 上 `rename` 覆盖已存在文件是原子的）。

   —— 落盘成 `�`。需改为代理对安全截断。

2. **`claude.js` 超时只 kill 父进程**（[claude.js:140](../../../D--QQBOT/qq-bot/src/claude.js)）
   —— conhost 残留会让 `close` 事件永不触发，超时分支被挂住。应改为杀进程树
   （`taskkill /T /F`，与 pm2 同样的做法，因为没有 IPC 拿不到干净退出）。

3. **关闭时子进程未清理**（[index.js:314](../../../D--QQBOT/qq-bot/src/index.js)）
   —— `shutdown()` 里只 `process.exit(0)`，不杀在跑的 claude。
   *注：pm2 路径下这个处理器本来就不会触发（见约束 1），此修复只对「终端里 Ctrl+C」有意义。*

## 已知限制（明确不解决）

### 重放 `queued` 条目也可能重复执行——说清边界

「`queued` 确定未执行」这句话**只在写入成功的前提下成立**。误判来自这三处：

1. `markRunning()` 执行了但**写盘失败**（磁盘满、文件锁），而 claude 照常跑完
   → 条目仍是 `queued` → 重启后重放 → **破坏性操作执行两次**
2. 队列文件损坏，恢复时当作空队列 → 该条目**静默丢失**（所幸退回改造前的现状，即丢弃）
3. 进程在 `markQueued` 之后、claude 启动之前被杀 → 条目是 `queued`，重放安全（这是正常路径）

所以「永远不会重复执行」是**不成立**的说法。准确表述是：

> 重复执行的前提是「写盘失败」，属异常路径；正常路径下 `queued` 条目确实未被执行过。

**这两处必须显式处理，不能靠假设**：
- `markRunning()` 写盘失败必须 `log` 告警（写失败在队列里是静默的）
- 队列文件解析失败必须 `log` 告警，不能悄悄从空队列开始

### 反向风险：漏执行

条目已标 `running`、claude 正在执行破坏性动作时被杀 → 我们丢弃它 →
那是**漏执行**而非重复执行。对这台以 Administrator 权限跑、且关闭了全部权限确认的机器来说，
少做一次比多做一次安全。

### 重复回复

用户已确认可接受：**优先不丢消息**。
